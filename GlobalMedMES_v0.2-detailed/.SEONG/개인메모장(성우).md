JPQL(Java Persistence Query Language)
엔티티 객체를 조회하는 객체지향 쿼리
테이블을 대상으로 쿼리하는 것이 아니라 엔티티 객체를 대상으로 쿼리한다.

네이티브 쿼리(Native Query)



JPQL과 네이티브 쿼리 둘다 데이터를 조회하는 방식
JPQL은 직접적으로 데이터베이스에 요청을 보내서 조회하는게 아니라 엔티티 객체를 통해 조회하는 방식으로
SQL과 비슷하지만 테이블의 컬럼이 아닌 엔티티의 요소를 통해 조회하며 해당 엔티티와 연결된 테이블로 자동으로 변환되어 사용된다.
또 그렇기에 데이터베이스 문법에 독립적으로 사용할 수 있으며 어떤 DB를 쓰더라도 자동으로 그에맞게 변환되어 사용된다.

네이티브 쿼리는 JPA를 통하지 않고 DB에 있는 원래 SQL 그대로 보내는 쿼리로 JPQL이 엔티티를 이용하여 조회를 한다면 네이티브 쿼리는 DB의 테이블, 컬럼을 그대로 사용하여 조회한다.
JPQL을 사용하여 조회하기 어려울때 네이티브 쿼리를 사용하여 조회를 한다.
JPQL을 거치지 않고 DB에 맞는 SQL을 직접 실행 하므로 DB 테이블과 컬럼 이름을 그대로 사용해야 한다
DBMS에 종속적이기에 DB가 변하면 SQL 문법도 바꿔야할 필요가 있다.
보통 JPQL로는 표현하기 힘든 복잡한 SQL (예: DB 함수, 조인, 윈도우 함수 등)을 쓸 때 사용한다.


PrePersist = 데이터가 들어가기전 자동으로 해당 데이터를 점검하는 규칙
예 : 
@PrePersist
void prePersist() {
    // 1) defectQty가 null이면 기본값 0으로 세팅
    if (defectQty == null) defectQty = BigDecimal.ZERO;

    // 2) 현재 로그인한 사용자 정보를 SecurityContextHolder에서 꺼냄
    Authentication a = SecurityContextHolder.getContext().getAuthentication();

    // 3) createdBy 필드가 비어있으면 로그인한 사용자의 이름 또는 "system"으로 세팅
    if (createdBy == null || createdBy.isBlank()) {
        createdBy = (a != null && a.isAuthenticated()) 
            ? String.valueOf(a.getPrincipal()) // 로그인한 사용자
            : "system"; // 로그인 정보 없으면 "system"
    }
}

### KPI 측정의 핵심: 유효 작업 시간

MES의 핵심 KPI 중 하나인 **설비 가동률**이나 **OEE(종합 설비 효율)**는 단순히 24시간 중 얼마나 가동했는지를 보는 것이 아닙니다. 기계가 **실제로 가동할 수 있었던 시간(계획된 가동 시간)**을 기준으로 삼아야 합니다.

**계획된 가동 시간 = 총 시간 - (계획된 비가동 시간)**

- **총 시간**: 하루 24시간 또는 주 7일과 같이 전체 시간을 의미합니다.
- **계획된 비가동 시간**:
    - **정기 휴게 시간**: 식사 시간, 휴식 시간
    - **정기 점검 시간**: 설비 청소, 예방 점검
    - **비가동 날짜**: 공휴일, 정기 휴무일, 주말

### KPI 산출 방법

KPI는 '계획된 가동 시간'을 분모로 사용하여 계산합니다.

- **가동 시간**: 설비가 실제로 제품을 생산하며 동작한 시간
- **비계획 비가동 시간(다운타임)**: 설비 고장, 원자재 부족, 작업자 부재 등 계획되지 않은 이유로 멈춘 시간

**가동률 = (가동 시간 / 계획된 가동 시간) x 100%**


데이터베이스 DSL

수율 계산 %
(양품 수량 ÷ 총 수량) × 100
불량품 계산 %
(불량 수량 ÷ 총 수량) × 100
OEE %
(양품률 × 가동률) × 100
생산속도
총 생산 수량 ÷ 가동 시간(시간단위)

보통 객체 관계나 데이터베이스 연관에서 쓰이는 개념이에요.

가벼운 연결 (Lightweight Association)
객체 간 참조는 있지만 실제 데이터를 바로 가져오지 않음
필요할 때만 DB에서 조회
예: Lazy Loading 방식의 관계

깊은 연결 (Deep Association / Eager Association)
객체를 가져올 때 관련 객체도 같이 가져옴
즉시 모든 연관 데이터를 DB에서 로딩
예: Eager Loading 방식의 관계

핵심: 가벼운 연결은 지연 조회, 깊은 연결은 즉시 조회라고 생각하면 돼요.


aggration type 알아보기
데이터나 KPI 등에서 집계 방식을 의미함
예를 들어 KPI 데이터라면:
REALTIME → 실시간으로 데이터를 집계
DAILY_BATCH → 하루 단위로 모아서 집계
필요에 따라 주 단위, 월 단위 등도 가능

DDD 알아보기
Domain-Driven Design
소프트웨어 설계 방법론 중 하나

도메인(비즈니스 핵심 영역) 중심으로 설계

핵심 개념:
Entity: 고유 식별자를 가진 객체 (예: 회원, 주문)
Value Object: 고유 ID 없이 속성으로만 의미 있는 객체 (예: 주소, 좌표)
Aggregate: 관련 객체 묶음, 외부에서 접근할 때 루트(Entity)만 접근
Repository: DB와의 통신을 캡슐화
Service: 도메인 로직 수행
핵심: 비즈니스 규칙을 코드에 바로 반영하고, 모델을 현실 세계 도메인과 최대한 가깝게 만드는 설계 방식

Lazy Loding 알아보기

데이터베이스에서 객체를 실제 필요할 때 가져오는 방식
장점: 불필요한 데이터 로딩 방지 → 성능 최적화
단점: 필요할 때마다 DB 쿼리 발생 → 너무 많이 쓰면 오히려 성능 저하
예: JPA에서 @ManyToOne(fetch = FetchType.LAZY)
반대 개념: Eager Loading (FetchType.EAGER) → 연관 객체를 바로 가져오기

CREATE TABLE `tb_employee` (
  `employee_id` VARCHAR(36) NOT NULL COMMENT '직원 ID (PK, FK→tb_user.user_id)',
  `employee_number` VARCHAR(50) NOT NULL COMMENT '직원 번호',
  `employee_name` VARCHAR(100) NOT NULL COMMENT '직원 이름',
  `is_deleted` TINYINT DEFAULT 0 COMMENT '소프트삭제 플래그',
  `deleted_at` DATETIME NULL COMMENT 'UTC',
  `created_by` VARCHAR(50) NOT NULL,
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT 'UTC',
  `modified_by` VARCHAR(50) NULL,
  `modified_at` DATETIME NULL ON UPDATE CURRENT_TIMESTAMP COMMENT 'UTC',
  PRIMARY KEY (`employee_id`),
  UNIQUE KEY `uk_employee_number` (`employee_number`),
  CONSTRAINT `fk_employee_user` FOREIGN KEY (`employee_id`) REFERENCES `tb_user`(`user_id`) ON DELETE RESTRICT
) ENGINE=InnoDB COMMENT='직원 정보: tb_user와 1:1 관계로 직원의 기본 정보를 관리.';

직원 정보: tb_user와 1:1 관계로 직원의 기본 정보를 관리.

자격증 테이블(cert) 제작
자격증 또는 스킬을 적어놓는 테이블

-- tb_cert (자격증 마스터)
CREATE TABLE `tb_cert` (
  `cert_id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '자격증 ID (PK)',
  `cert_code` VARCHAR(50) NOT NULL COMMENT '자격 코드 (유일)',
  `cert_name` VARCHAR(100) NOT NULL COMMENT '자격 명칭',
  `cert_description` VARCHAR(255) NULL COMMENT '설명',
  `cert_valid_period_months` INT NULL COMMENT '유효기간 (월 단위, NULL=무기한)',
  `is_deleted` TINYINT DEFAULT 0,
  `deleted_at` DATETIME NULL,
  `created_by` VARCHAR(50) NOT NULL,
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  `modified_by` VARCHAR(50) NULL,
  `modified_at` DATETIME NULL ON UPDATE CURRENT_TIMESTAMP,
  PRIMARY KEY (`cert_id`),
  UNIQUE KEY `uk_cert_code` (`cert_code`)
) ENGINE=InnoDB COMMENT='자격 마스터: 설비/공정 필요 자격 정의';


cert_code 는 시스템이 효율적으로 처리하기 위한 코드
cert_name 사람을 위한 필드 언제든 자유롭게 수정할 수 있으며, UI나 보고서에 표시되는 용도로 사용
cert_code 시스템을 위한 필드 변하지 않는 고유한 값으로, 프로그램 로직이나 데이터베이스 연결에 사용
description은 해당 자격증에 대한 상세하고 부가적인 정보를 담는 데 사용됩니다.


cert_code는 아이디랑 비슷함
cert_code를 FK로 사용해도 되지만 FK의 효율을 떨어지기에 cert_id를 사용함

cert_id: 사내에서 쓰는 자격증 아이디
cert_code: "E_ForkLift"
cert_name: "지게차 운전 교육 이수"
description: "3톤 미만 지게차 운전 가능."

출근 기록을 관리하는 테이블

-- tb_attendance (근태 기록)
CREATE TABLE `tb_attendance` (
  `attendance_id` BIGINT NOT NULL AUTO_INCREMENT COMMENT '근태 기록 ID (PK)',
  `employee_id` VARCHAR(36) NOT NULL COMMENT '직원 ID (FK→tb_employee.employee_id)',
  `attendance_date` DATE NOT NULL COMMENT '근태 기록일',
  `attendance_check_in_time` DATETIME NOT NULL COMMENT '출근 시간 (UTC)',
  `attendance_check_out_time` DATETIME NULL COMMENT '퇴근 시간 (UTC, 퇴근 전이면 NULL)',
  `attendance_code_id` BIGINT NOT NULL COMMENT '근태 상태 코드 ID (FK→tb_code, 예: 정상, 지각, 조퇴)',
  `attendance_remarks` VARCHAR(255) NULL COMMENT '특이사항 기록',
  `is_deleted` TINYINT DEFAULT 0 COMMENT '소프트삭제 플래그',
  `deleted_at` DATETIME NULL COMMENT 'UTC',
  `created_by` VARCHAR(50) NOT NULL,
  `created_at` DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP COMMENT 'UTC',
  `modified_by` VARCHAR(50) NULL,
  `modified_at` DATETIME NULL ON UPDATE CURRENT_TIMESTAMP COMMENT 'UTC',
  PRIMARY KEY (`attendance_id`),
  UNIQUE KEY `uk_attendance_date_user` (`attendance_date`, `employee_id`),
  KEY `idx_attendance_user` (`employee_id`),
  KEY `idx_attendance_date` (`attendance_date`),
  CONSTRAINT `fk_attendance_emp` FOREIGN KEY (`employee_id`) REFERENCES `tb_employee`(`employee_id`) ON DELETE RESTRICT,
  CONSTRAINT `fk_attendance_status_code` FOREIGN KEY (`attendance_code_id`) REFERENCES `tb_code`(`code_id`) ON DELETE RESTRICT,
  CONSTRAINT `ck_attendance_time_order` CHECK (`attendance_check_out_time` IS NULL OR `attendance_check_out_time` >= `attendance_check_in_time`)
) ENGINE=InnoDB COMMENT='근태 기록: 직원의 실제 출근/퇴근 시간을 관리. 동일 날짜/사용자 중복 방지(UTC).';

RESTful 원칙
RESTful API에서 POST는 새로운 리소스를 생성하는 데 사용됩니다. 당신의 경우, "출퇴근 기록"이라는 새로운 리소스를 생성하는 것이죠. 이 리소스의 정보는 **요청 본문(request body)**에 담아 보내는 것이 가장 자연스럽습니다.

POST /user/attendance라는 URL은 "출퇴근 기록을 생성한다"는 명확한 의미를 가집니다. 반면, POST /user/attendance/CHECK_IN은 "체크인이라는 상태를 통해 출근 기록을 생성한다"는 다소 복잡한 의미가 됩니다.

결론적으로, 현재 코드는 아주 잘 설계되어 있습니다. 깔끔한 URL과 확장 가능한 DTO 구조를 갖추고 있어서 향후 기능 추가에도 유연하게 대처할 수 있습니다.
