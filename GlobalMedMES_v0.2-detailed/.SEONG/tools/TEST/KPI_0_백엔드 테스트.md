----production_log
    작업지시를 새로 내리고 그 작업지시의 상태를 P에서 R로 바꾸면 STARTTIME이 기록됨
    이후 Perfomance를 생성하면 그걸 기반으로 얌품의 개수와 불량품의 개수가 기록됨
    작업지시의 상태를 R에서 C로 바꾸면 ENDTIME이 기록됨

----definition
    테이블 내부의 식을 기반으로 계산을 함
    수율, 불량률, 시간당 생산량, OEE의 식이 있음
    실제로 4개가 전부 동작하는 걸 확인함
    현재(09-02) OEE는 작동시간이 100이기 때문에 수율과 같은 값이 나옴

----kpi_data
---리얼타임
    ProductionPerfomance를 기반으로 새로운 Perfomance로 Service를 요청하면
    KPI REALTIME이 생성되어 저장됨

---계획 내인거
    POST perfomance를 실행했을때 새로운 KPI가 저장됨
    -날짜, 워크오더, 공정, 설비, 아이템을 기준으로 해서 새로운 아이디가 계속해서 저장됨
    같은 날짜, 워크오더, 공정, 설비, 아이템을 가지고 있을때
    -해당 데이터를 업데이트 함


---배치
    @Scheduled(cron = "0 * * * 1 ?") 
    을 사용하여 1분마다 코드가 기록되는지 확인했음

---계획 내인것
    일일 배치 계산 시 실적이 없으면 아무 작업도 하지 않음
    일일 배치 계산 시 만들어진 테이블이 없다면 새로 만들어서 내용을 배치함
    일일 배치 계산 시 날짜, 설비, 공정, 아이템 중 하나라도 다르면 새로운 테이블에 배치하고 모두 같다면 기존 테이블을 업데이트 함

---계획 외였던것

--시간 오차
    시간기준이 예상외인 상태였음
     2025-08-31 00:00:00 ~ 2025-09-01 00:00:00 사이의 시간을 가져오려 했는데
     2025-08-30 17:30:00 ~ 2025-08-31 09:15:00 사이의 시간을 가져오는 중(오차 있음)
     
     yesterdayUtc = 어제 날짜
     startOfDay = 어제 날짜T 00시 00분
     endOfDay = 오늘 날짜T 00시 00분

     starttime 00시부터 endtime 24시 사이인 것을 repo에서 제대로 가져오는 중
     데이터베이스에선 starttime이 2025-08-31 15:00:00이라고 적혀있는데 이걸 가져온 레포지토리는 2025-09-01T00:00이라고 적음

    아무래도 위의 내용은 내가 착각한거 같음 24시에서 UTC기준인 9시를 빼면 15시니까 그 기준으로 
    다음 00시인 15시까지 가져오는게 맞는거 같음


    calc_at도 시간이 현재시간(KTC)보다 18시간 늦게 들어감
    스프링부트도 UTC기준이라 9시간 늦게 가는데 TIMEZONE 지정을 잘못해서 한번더 9시간 전을 쟀던것 같음
